BUG 1  KRR coefficient mapping misaligned (in both e3_main.py and e3b_krr_sweep.py)
======================================================================================
The design columns run (rh_0, n_0, rh_1, n_1, ...): column 2k is rh_k and column 2k+1 is n_k.
The old script rebuilt the pair force as c[k]*P_k*rh + c[K+k]*P_k*n, which does not match that order.
same coefficient vector c (K=120, h²=0.4):
  taking (2k, 2k+1) as the column order: reference pair force, law error NMSE = 0.0002116
  taking (k, K+k) as the old code did: relative force difference 2.771, law error NMSE = 7.672
  => the old convention is 36251.5 x worse than the correct one. The KRR column of E3/E3b is void.

BUG 3  memory: the old version materialised the whole palette at once
======================================================================================
In old e3_main.krr_build, `((Un[:,None,:]-cen[None,:,:])**2).sum(-1)` has len(Un)×K×3 elements.
training pair configurations in this mid-regime run (measured) = 585577
    K=200 -> 585577×200×3×8B = 2.62 GB (single allocation)
    K=600 -> 585577×600×3×8B = 7.85 GB (single allocation)
measured (peak working-set increase of a child process on synthetic points of the same size):
  points   K        old          new (30k subsample)
  585577   60       1608.39 MB / 0.9s 83.53 MB / 0.4s
  585577   120      3216.73 MB / 2.0s 165.94 MB / 0.9s
  585577   200      5360.58 MB / 3.6s 275.81 MB / 1.5s
  => the old version grows linearly with K; the new one subsamples and is independent of K. Linear extrapolation to K=600 = 7.9 GB.

BUG 10  E6 matched the triplet force to the residual along the wrong axis (only flips the sign, but the reported numbers are wrong)
======================================================================================
    Old e6: f3_true[j] = f3(Xd[t]) broadcasts the per-particle force (N,d) onto axis 1 (columns) of (N,N,d),
    while the residual resid[t,i,j] is the pair force on i from j, which belongs on rows (i).
    The pair residual is antisymmetric in (i,j) (f_ij = −f_ji), so column matching = row matching negated:
      old report cosine  −0.1559 / −0.1569 / −0.1476
      correct matching  +0.1559 / +0.1569 / +0.1476
    New exp/e6.py prints both; measured max |cos_row| − |cos_col| = 0 (see reports/E6.txt).
    => the conclusion stands (|cos|≈0.15 < 0.7, condition B still fails and the claim stays in the appendix), but the sign has to be corrected when citing.

BUG 9  the degeneracy ratio is undecidable in this setting (the direction flips after the fix)
======================================================================================
    Re-measured after fixing the KRR mapping (exp/e3.py):
      AFR-sym   covered 4.672e-09   uncovered 4.402e-08   ratio 9.42
      KRR-pair  covered 3.848e-05   uncovered 2.063e-04   ratio 5.36
      NN-pair   covered 1.474e-03   uncovered 5.547e-03   ratio 3.76
      KRR(old map) covered 3.739     uncovered 3.018      ratio 0.81
    => when both quantities sit at rounding level (1e-9/1e-8) the ratio is noise: the symbolic 9.42 and the old 0.87
      are both quotients of machine-precision numbers. Judging C1 by the degeneracy ratio neither holds nor fails here —
      the criterion has to change (e.g. absolute error in the uncovered region < 1e-6), and separately explain why the symbolic form
      already reaches rounding level in the covered region (the basis contains the true family).
    The old KRR uncovered error of exactly 1.000 is another fingerprint: the local kernel has no support outside the training range,
      so the prediction is ≈0 and the NMSE is exactly the 1 of always predicting zero.

A defect of the same kind that the gates caught in my own new code (kept as a positive example)
======================================================================================
    The first CUDA Graph path in tl/sim.py stored a frame every integration step, while every=4 wants one every 4 steps.
    Symptom: E0's |x|max went from 1.00984 to 0.857619 and every other metric was off.
    How it was caught: comparing old numpy / new eager / new graph one by one over every ∈ {1,4,5,32,64}.
    After the fix the three agree to ≤ 2.8e-16 (see tests/test_parity.py).
